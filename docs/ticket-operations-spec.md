# 咲楽ノ宮｜チケット対応 運用仕様

**決定事項まとめ v0.1｜2026年11月26日（日本時間）**

対象：お問い合わせ・相談・通報など、運営が対応するチケット。
このチャットで確認した運用ルールをまとめた資料です。実装済み・本番反映済みを示すものではありません。

## 1. 基本の流れ

受付 → 主担当の決定 → 対応 → 相談者への解決確認 → 完了。

- 同じ内容の相談は、過去のチケットを引き継いで再開する。
- 別の内容の相談は、新しいチケットとして扱う。
- 自動受付の案内と、運営による最初の返信を区別する。

## 2. 受付フォームと受付案内

| 項目 | 入力 |
| --- | --- |
| 相談・通報の内容 | 必須 |
| 希望する対応 | 任意 |
| 日時・場所・相手 | 任意 |
| 証拠の画像・ファイル | 任意 |

受付直後に、受付番号・現在の状態・返信の目安を自動案内する。この自動案内は、運営による初回返信には数えない。

相談者は「緊急の安全問題」を選択できる。運営は内容を確認して、後から緊急度を変更できる。

## 3. 主担当と補助

- 対応できる運営が「担当する」を押し、主担当を1人決める。
- 他の運営も補助できる。返信や進捗管理の責任者は主担当とする。
- チケットの種類ごとに、担当できるロールを設定する。
- 宮司・神職は全種類に対応できる。ただし、当事者になっている案件の主担当・判断役からは外れる。

### 担当交代

- 通常は、主担当が引き継ぎを依頼し、新しい担当者が承諾した時点で交代する。
- 引き継ぎ先が決まるまでは、元の主担当を残す。
- 長期不在や当事者化などの場合、宮司・神職が主担当を変更できる。
- 担当の変更理由は履歴に残す。

## 4. チケットの5つの状態

| 状態 | 意味・動き |
| --- | --- |
| 未対応 | 主担当を決めて、運営の対応を始める段階 |
| 対応中 | 運営が内容を確認し、回答や対応を進めている段階 |
| 相談者の返信待ち | 運営から質問・確認を送り、相談者の回答を待っている段階 |
| 運営内の確認待ち | 運営側の確認・判断・相談を待っている段階 |
| 完了 | 解決確認後、または返信なしで終了した案件 |

相談者の返信待ちに返信が来たら「対応中」へ戻し、主担当へ通知する。返信待ちの確認通知・自動終了タイマーは解除する。

運営内の確認待ちは、自動完了にしない。

## 5. 期限と通知の初期値

以下の日数・時間は固定値ではなく、設定で変更できる初期値。

| 項目 | 初期値 | 対応 |
| --- | --- | --- |
| 初回返信の目安 | 受付から24時間以内 | 運営が一度返信する。即解決できない場合も受付確認・今後の見通しを伝える |
| 初回返信なしの確認通知 | 受付から24時間 | 主担当へ1回通知。未担当なら担当ロールへ通知 |
| 初回返信なしの上位通知 | 受付から48時間 | 宮司・神職へ1回通知 |
| 相談者の返信待ちの確認通知 | 返信待ち開始から3日 | 相談者へ返信確認の通知 |
| 相談者の返信なし自動完了 | 返信待ち開始から7日 | 返信がなければ「返信なしで終了」として記録 |
| 対応中の進捗確認 | 3日間進展なし | 主担当へ確認通知 |
| 運営内の確認待ちの進捗確認 | 3日間進展なし | 主担当へ確認通知。自動完了はしない |

初回返信の目安と確認通知の時間も、それぞれ変更できる項目として扱う。

## 6. 設定の管理

- 時間・日数は、項目ごとに変更できる。
- チケットの種類ごとに設定できる。
- 種類別に未設定の項目は、共通設定を使う。
- 設定を変更できるのは、宮司・神職。
- 誰が何を変更したか、履歴に残す。
- 日数設定の変更は、新規チケットから適用する。
- 対応中のチケットは、受付時の設定を維持する。途中の設定変更で突然終了させない。

## 7. 完了と完了理由

- 主担当が対応結果を伝え、相談者に解決したか確認してから完了にする。
- 手動で完了にするときは、主担当が「対応内容・結果」を短く記録する。
- 完了操作ができるのは、主担当・宮司・神職。
- 「解決して完了」と「返信がなく終了」を区別して記録する。
- 返信がないまま終了した案件を、解決済みとして数えない。

完了したチケットは対応中の一覧から外す。「完了履歴」から内容を確認・再開できるようにする。

## 8. 再開

- 同じ内容の追加相談・確認は、過去のチケットを引き継いで再開する。
- 再開できるのは、相談者本人・主担当・宮司・神職。
- 再開時は「未対応」に戻し、主担当を決め直す。
- 返信期限は、再開時刻から数え直す。
- 過去の会話・対応結果・履歴を引き継ぐ。

## 9. 閲覧範囲・内部メモ・相談者への通知

### チケットと履歴

閲覧できるのは、相談者本人・その種類の担当ロール・宮司・神職。

### 内部メモ

- 相談者への返信とは別に、運営専用の内部メモを残せるようにする。
- 内部メモを閲覧できるのは、その種類の担当ロール・宮司・神職。
- 確認中の内容や引き継ぎ事項を記録する。
- 相談者への返信と区別し、誤送信を防ぐ。

### 相談者への通知

- チケット内への通知を基本にする。
- DMには更新のお知らせとリンクだけを送り、相談本文は広げない。
- DMを受け取れない人も、チケットで確認できるようにする。

## 10. 通報・緊急対応・最終判断

### 当事者の除外

通報対象者や当事者になっている運営は、その案件の主担当・判断役から外し、関係のない運営が対応する。

### 相手への情報共有

通報者の名前やチケット本文は原則そのまま相手へ共有しない。事実確認に必要な内容を、運営から相手へ伝える。

### 緊急時

- 荒らし・脅迫・個人情報の流出など、安全に関わる通報は、受付時点で宮司・神職へ即通知する。
- 通常の初回返信の目安とは別に、早く気づけるようにする。
- 被害が進行している場合は、制限操作の権限を持つ運営が一時的な制限を行える。
- 一時制限後は、対応内容と理由を宮司・神職へ速やかに報告する。

### 処分の最終判断

主担当が事実・証拠・対応案を整理し、当事者ではない宮司・神職が最終判断する。

## 11. 履歴と添付資料の保存

| 項目 | 初期値・ルール |
| --- | --- |
| 履歴の保存期間 | 完了から180日。種類ごとに変更可能 |
| 保存延長 | 必要な案件は宮司・神職が延長可能 |
| 画像・ファイル | 本文と同じ期間保存する |
| 添付の閲覧範囲 | 本文と同じ |
| 1ファイルの保存上限 | 初期値25MB。宮司・神職が設定で変更可能 |
| 1チケットの添付保存合計 | 初期値100MB。宮司・神職が設定で変更可能 |

チケット本文と添付資料を一緒に確認できるようにし、添付リンク切れで説明資料や証拠が見られなくなることを防ぐ。

## 12. 運営の対応一覧

- 自分に閲覧権限のある案件だけを表示する。
- 緊急・期限超過の案件を優先表示する。
- 種類・主担当・状態・期限を確認できるようにする。
- 完了案件は通常の対応一覧から外し、完了履歴で確認する。

## 13. 実装前に詰める細部

以下は、まだ決定済みとして扱わない。実装する際に、既存システムとの整合を確認する。

- チケットの具体的な種類、種類ごとの担当ロール、通知先。
- 状態の変更操作を主担当・補助担当のどこまで許可するか。
- 「3日間進展なし」の起点になる操作と、通知後も進展がない場合の再通知間隔。
- 解決確認待ちの扱い、相談者からの取り下げなど、追加の完了理由。
- 再開した案件の設定値、再開後に旧担当者が権限を失っていた場合の操作。
- 当事者になった運営の閲覧権限をどう扱うか。主担当・判断役から外すことは決定済み。
- 保存期限の予告、延長の単位、期限到達後の削除方法、再開時の保存期限。
- 添付上限を超えた場合の案内、保存失敗時の通知・再試行、既存の添付の移行。
- Discordのチャンネル・履歴画面・再開操作をつなぐ具体的な実装方式。

この資料は運用の合意事項であり、これらの細部を推測で確定したり、既存チケットを自動変更したりするものではない。


## 14. v0.1の実装判断（運用合意とは区別）

- 新規の通常種類だけを対象とし、既存案件・面接・有料依頼は変更しない。
- 補助担当は公開返信と内部メモ、主担当と宮司・神職は状態・完了・引き継ぎを操作する。
- 進展の起点は人の返信・内部メモ・状態変更・引き継ぎ等。起点ごとに進捗通知は1回、再開は新しい初回返信の時計を開始する。
- 当事者に指定した運営はWebの閲覧からも除外する。Discord管理者権限の制約は説明書に記載する。
- 再開しても受付時の期限設定を維持する。保存期限は対応中に解除し、次回完了から起算し直す。
- 添付の失敗時は削除前に保存を再試行する。上限超過分は保存対象外として相談者に案内する。
- 取り下げ・期限前の予告等は今回追加しない。処分の最終判断は運営が行い、BOTが処分を自動決定するものではない。
