## 点検の範囲と変更

| 分野 | 確認した問題 | 修正 |
|---|---|---|
| Web素材とメモリ | カード474画像などをWeb起動時に一括読み込みし、使われない素材も保持 | 大きな画像・動画・バッジの描画を遅延化。遅延素材のキャッシュを合計16MiBのLRUで制限 |
| 宿の掲示板とDB | 部屋ごとに受付状態を問い合わせる | 表示対象の受付状態を1回のSQLで取得。未設定・受付・話題の検査は個別取得と同じ |
| 更新の集中 | 掲示板の更新依頼をすべて待ち行列へ積む | 実行中の依頼を集約し、最後の最新状態を反映。失敗後も次の更新を受け付ける |
| 静的素材の再送 | 条件付き再取得で本体を省く仕組みがない | 弱いETagを付け、If-None-Match一致時は304で本体を省略 |
| 診断ログ | Discord APIのエラーに応答用トークンURLや認証情報が含まれ得る | エラーのコード・種類・場所を保ち、URL内トークンや入れ子の認証情報を伏せる |
| Discordコマンド | 持ち物・カジノはDB処理後に最初の返事をするため、3秒を超えると受付に失敗し得る | DB処理前に本人だけに受付を返し、完了後に結果を更新。持ち物の取得失敗も案内する |

料金・銭・券・抽選・入室権限・データ形式の変更やマイグレーションはありません。宿のボタンID重複は担当側の `ea7c568b` で修正済みのものを引き継ぎ、再実装しません。

同じローカル環境で、基準版と変更版のビルド済み素材モジュールをそれぞれ新規Nodeプロセスへ読み込み、GC後に計測しました。Web全体・BOT全体・本番VPSの使用量ではありません。

起動直後のRSS差は203.5MiB（約43％）です。カード画像の合計59.5MiBと登録件数は同じで、画像の画質を落としたものではありません。RSSにはネイティブ処理やアロケーターの確保分もあり、1回の測定値を本番全体の削減率として使うことはできません。

16MiBは遅延読み込みした素材のキャッシュ保持分です。もともとの小さな素材・文字列、同時配信中の応答、GC前の一時領域を含むプロセス全体の上限ではありません。初回や追い出された素材はファイルから読むため、キャッシュとI/Oの交換条件があります。

生の計測値は [計測JSON](performance/2026-11-21-static-assets.json)。変更版の再計測は、`npm run build` 後に `node --expose-gc scripts/benchmark-static-assets.mjs` で行います。第1引数に基準版のビルド済みassets.jsを渡すと同じ手順で比較できます。
